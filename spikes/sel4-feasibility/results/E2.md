# E2: two isolated Rust tasks over seL4 IPC, with refused attempts to exceed their authority

**Outcome (agent's reading): Pass, label U, functional only.** A root task built two tasks, each with its own address
space, CNode, TCB and IPC buffer. They exchanged calls over one endpoint. The client made two attempts to exceed its authority
(forging a badge, reading the server's memory) and two invalid invocations (an empty slot, an invalid method on a CNode capability
it holds); the first two were refused, the second two returned errors, and the root task received a message on its fault endpoint
that has the shape of the client's VM fault at the server's address (see "What the fault check shows"). 3 of 3 boots, under QEMU 11.1.3 TCG,
on the E1-H kernel configuration [Measured: [E2/10-boot-1..3](E2/)]. The owner provisionally accepted it as Pass (U), subject to independent review, and after the review **finally accepted it as Pass (U)**, limited to its demonstrated functional and capability-isolation probes; it does not establish verified kernel-generated fault delivery (plan Amendments, 2026-11-09). It is not
Stage B, P1 or P2 evidence: A2a has not run, and nothing here is about HVF, SMP, performance, hardware, revocation, or
the formal assurance of seL4's isolation.

Authorization: the owner's "go ahead" and "Option 1, approve object" of 2026-11-09, then the approval of D19 and D20 for E2's scope, recorded in the plan's
[Amendments](../../../docs/research/sel4-spike-plan.md#amendments). Code: `crates/e2-task` (client and server),
`crates/e2-root-task`, `build-e2.sh`; no kernel, loader or E1/A1 root-task source changed.

## What the system does

| Step | Observed (identical in all three boots) |
|---|---|
| Root task | Allocates all objects from the largest non-device untyped, loads two ELFs into fresh frames (one set per task), maps one fresh granule at `0x50000000` in the **server's** space only, gives each task a CNode, starts them |
| Positive control | The server writes and reads back its secret: `E2_SERVER secret mapped and readable` |
| 1. IPC | Client `Call`s through its badged endpoint capability. The server sees badge `0xa11ce`, replies `42`, served-count `1`; the client checks all three |
| 2. Empty slot (an invalid invocation, not an authority test) | Invoking slot 5, never populated: reply label `2` (`InvalidCapability`). The kernel logged `Attempted to invoke a null cap #5`. This shows that slot is empty; it also rules out the client running in the root task's CSpace, where slot 5 is live |
| 3. Invalid method on a held capability (not an authority test) | Invoking its own CNode capability with label 0: `3` (`IllegalOperation`). seL4 dispatches by the capability's type, so the kernel treated this as a CNode invocation and refused it because 0 is not a CNode method [Documented: `src/object/cnode.c:53-57` at the pinned commit]; "as an endpoint" has no meaning to it. Any valid CNode label would have been carried out with the client's full rights over its own CNode. The kernel logged `CNodeCap: Illegal Operation attempted` |
| 4. Badge forgery (an authority test) | Minting a new badge from its already-badged endpoint capability: `Err(IllegalOperation)`. seL4 refuses any mint from an already-badged endpoint, whatever badge or rights are asked for; the client asked for a subset of its rights, so rights are not the cause [Documented: `objecttype.c:403-407`, `cnode.c:145-147,180-184`]. The kernel logged `Mutated cap would be invalid`. The verifier does not check the kernel's reason lines (this table cites them from the raw log) |
| Nothing leaked through | A second legitimate call returns served-count `2`: the server received no message from steps 2 to 4 |
| 5. Memory (an authority test) | The client reads `0x50000000`, which is mapped only in the server. The root task receives a message on its fault endpoint through the client's fault capability (badge 1), shaped as a VM fault at `0x50000000`, and prints `E2_PASS`. The client never prints the value, and no `E2_FAIL` appears. That a real fault occurred rests on the client's source, which never invokes its fault capability [Inferred: see below] |

## What the fault check shows, and does not

The root task prints `E2_ROOT client vm fault` when the first message on its fault endpoint (a) arrives with badge 1, (b) decodes
as a VM fault and (c) carries address `0x50000000`. Badge 1 exists only in the client's slot 4, so the server cannot have sent it
(the server's badge is 2). But the client holds a send capability (write and grant-reply) to that endpoint, because in non-MCS
seL4 the kernel looks the fault handler up in the faulting task's own CSpace, and it also holds a full-rights capability to its own
CNode (slot 3), with which it could move or delete that fault capability. **So the check establishes which capability sent the
message, not that the kernel generated a fault.** [Measured, by the reviewer] A scratch client that never reads the secret and
instead calls slot 4 with a hand-built message of VM-fault shape produced the same marker sequence, including `E2_PASS`, and would
pass the verifier. That the evidence run contained a real fault rests on the client source, in which slot 4 is never invoked
[Inferred], and on the evidence binaries matching the current source (the reviewer rebuilt them and the instruction streams
matched after normalising addresses [Measured by the reviewer]). The check does not read the fault status register or the
prefetch flag. A stronger check (read the client's registers with `tcb_read_registers` and require PC to equal the fault's
instruction pointer) would still not be a proof and was not added.

## Do the tests detect failure? (two mutants)

Mutant images were built in a scratch directory and the sources restored byte-for-byte [Measured: [06](E2/06-mutation-checks.txt)].

| Mutant | Expected | Observed |
|---|---|---|
| The client is also given a mapping at `0x50000000` | The memory test fails | The client reads `0x0` instead of faulting, prints `E2_FAIL client read the server's memory`, and `E2_PASS` is not printed |
| The "empty" slot is the live endpoint | The empty-slot test fails | The server receives an unexpected second message (`request=42`), the client prints `E2_FAIL client: empty slot was not refused with InvalidCapability`, and `E2_PASS` is not printed |

## Changes from the proposal made to the owner

- **Rights amplification through mint is not tested.** Mint masks rights to the intersection; it does not reject. Seeing the
  effect needs a second fault round-trip, which this design avoids (the root task never resumes a faulted task). Badge forgery
  and an invalid method on a held CNode capability are tested instead.
- **The tasks come from two separate binaries**, each loaded into fresh frames, so no code page is shared; the proposal had said
  one ELF with shared read-only code.
- **A positive control was added after the first run.** The first image (`e6e20010…`, 3 of 3 boots passed) did not show that the secret was
  readable anywhere, so a fault at `0x50000000` could have meant "mapped nowhere". The server now reads its secret back. The first
  run's logs are kept locally (`external/e2-superseded-first-run/`, gitignored) and are not the evidence.

## Later change to the build script

After E3 (D23 in [deviations](deviations.md)), `build-e2.sh` names the binaries it builds (`--bin e2-client --bin e2-server`, `--bin e2-root-task`). Without it, the E3 binaries added to the same crates were built by the root-task step and failed, so E2 could not be rebuilt with its own script.
The script hash recorded in `E2/04-post-checks.txt` (`4c0ecb69…`) is therefore no longer the file's. Nothing was rebuilt or rerun for E2, and E2's evidence is unchanged.

## Limitations

- **Debug kernel.** `seL4_DebugPutChar` is not mediated by a capability, so every task can print. A production configuration would not have it.
- **The root task holds every capability** and is the supervisor. The tasks each hold a badged capability with write and
  grant-reply rights to the root task's fault endpoint, because the kernel looks the fault handler up in the faulting task's own
  CSpace. Neither task's code uses it, but the client could (see "What the fault check shows"). The client also holds a full-rights
  capability to its own CNode (slot 3), which gives it no authority outside that CNode.
- **Mint is exercised by one test only,** and no mutant shows that a successful mint would be caught.
- **The E2 ELFs and the image embed absolute build paths** (including the home directory, from the Cargo cache and target
  directory). They are untracked and must not be published; their hashes depend on the build directory, not only on the source.
  The sanitized logs contain no such path.
- **Two authority tests, two invalid invocations and one memory read,** not an enumeration of what the client can reach. No revocation, no use after revoke, no
  untyped or IRQ authority, no second fault, no timing or side channel, no mutual distrust beyond these steps.
- **Half the RAM of A1** (one 512 MiB region, the hypervisor option's overlay), one vCPU, non-MCS, TCG only.
- **Unmodified upstream recipe.** Page-mapping and ELF-loading code is adapted from the `spawn-task` example at the pinned tag
  (BSD-2-Clause, attribution kept); the `unwrap`s were replaced by error returns. The D11 exception does not apply to this code and none was taken.
  One `static mut` page placeholder remains, as upstream, touched only through `addr_of!`; every `unsafe` block in the E2 crates (five) carries a `SAFETY` comment. The BSD-2-Clause licence text is not in the repository (only the SPDX tag and copyright line, as in `crates/root-task`).
- **Source changed after the evidence build, comments only.** After the independent review, doc comments in `crates/e2-root-task/src/main.rs` and `crates/e2-task/src/bin/client.rs` were corrected (same line counts). The binaries were not rebuilt. Other review items left as they are: the server prints its "readable" line even if the readback mismatched (its `E2_FAIL` line still fails the verifier), and there is no mutant for the mint test.
- **Dependency policy.** `cargo deny --frozen check advisories bans sources` passed offline for the new dependency [Measured by the reviewer; local advisory database of 2026-11-09, not recorded in `results/`].
- **Warnings.** The kernel link warns that `kernel.elf` has an RWX segment; E1 had the same. The GIC target-ID warning appears as in E1.
