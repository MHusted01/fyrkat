# A5 step 2: revoke while mapped (exploratory falsification experiment)

**Not an A5 outcome.** Authorized by the owner on 2026-11-10 as "a minimal exploratory revoke-while-mapped falsification experiment, provided its experimental design receives independent review and it remains entirely inside a disposable emulated environment". It runs only under QEMU TCG, changes no kernel, loader, dependency or ADR, and decides nothing about the design of K3. Labels as in AGENTS.md.

## 1. Design (written before any run; reviewed independently before the first boot, and changed as the review required: see the end of this section)

### Question

seL4 reclaims memory by `Revoke` on an untyped (or on a capability) followed by a retype of the untyped. The kernel does not know what an SMMU maps ([A5 proposal](../../../docs/research/a5-design-proposal.md), section 3). **If the CPU-side authority over a frame is revoked while a stage-1 SMMU translation still names its physical page, and the kernel then hands that memory out again, can the device still read and write it?**

### Arrangement

The step 1 arrangement: QEMU 11.1.3 `virt` with `iommu=smmuv3,highmem=off` and `edu` (stream `0x10`), the SMMU enabled by the root task with the driver of step 1 ([`smmuv3.rs`](../crates/e2-root-task/src/smmuv3.rs)), on the E1-H kernel (Rust loader) and on K2R (elfloader), three boots each. One root task plays three roles, kept apart in the code by which capabilities each uses:

- **the server** owns the SMMU and its tables, and a permanent second mapping, I/O address `0x100003000` to its own page **O**, through which it can see what the device's buffer holds;
- **the donor** holds a 4 KiB untyped **U** and the frame **F** retyped from it;
- **the victim** receives whatever the kernel makes of U's memory after the donor has revoked it.

That all three are one task is a limit: the experiment shows what the kernel and the SMMU do, not what an untrusted donor in its own capability space can do (E2 and E3 are the evidence for separate capability spaces).

### Scenarios, in the order they run

Each starts with a **positive control**: with F mapped at I/O address `0x100000000`, a round trip through the device reaches F (16 of 16 words). A scenario whose control fails is void, and so is a run in which the device does not report a transfer finished.

**A. Naive reuse of a frame.** The server maps F for the device and also keeps a copy of F's capability (to test whether a copy pins the memory). The donor revokes U. Checked: both F's capability and the server's copy are gone. The donor retypes U into a new frame **G** and maps it; checked: G's physical address equals F's, and G reads as zero (the kernel cleared it). The victim writes a secret into G. Then, with the SMMU mapping never touched: (1) the device reads `0x100000000` into its buffer and writes the buffer to O: *how many of the secret's 16 words appear in O?* (2) the device loads an attack pattern from O and writes it to `0x100000000`: *how many of G's 16 words change?*

The outcome of a scenario is fixed by this rule, in the root task and again in the verifier: **REACHED** if all 16 words were read out and all 16 overwritten and no transfer left an event record; **REFUSED** if none was read out, none overwritten, and each of the two transfers left 16 translation-fault records for this stream, direction and page; anything else **MIXED**, which is a result that needs explaining, not a pass or a fail.

**B. Control: teardown before reuse.** As A, but before the donor revokes U the server clears the table entry, issues `CMD_TLBI_NH_VA` and `CMD_SYNC`. The same two device transfers follow. B differs from A in the order of teardown and revoke and in nothing else that bears on the SMMU, so it shows whether what A observes is caused by the surviving translation, and that the experiment can come out the other way. On the way B notes one kernel rule: a retype of U attempted while F's capability still exists. (That rule holds whoever holds the capability; it says nothing about who should.)

**C. Naive reuse as a kernel object (runs last).** As A up to the revoke; then the donor retypes U into a **CNode** of 128 slots (4 KiB) and mints a badged notification capability into slot 1. (1) *Disclosure:* the device copies the first 64 bytes of the page to O: are the raw words of slot 1 there, including the badge the root task chose? (2) *Duplication:* first, as a control, a `CNode_Copy` out of slot 2 is attempted and must be refused (the slot is empty). Then the device copies the 32 bytes of slot 1 onto slot 2. Is a `CNode_Copy` out of slot 2 now accepted, and does a signal through that copy arrive at the notification with the badge? (3) *Revocation:* a second copy of slot 1 is made **by the kernel** (the control: it is in the derivation list); then the notification's original capability is revoked. Are the minted capability and the kernel-made copy gone, and does a signal through the device-made duplicate still arrive?

The duplicate creates **no authority the root task did not already have**: it names the same object with the same badge and rights. What C asks is whether a capability can come to exist outside the kernel's bookkeeping. After C nothing may delete the CNode, slot 2 or the duplicate's copy: their list links are stale and a deletion would unlink through them. The experiment ends there and the machine is discarded.

One build-time mutant: **`teardown-without-invalidation`**, scenario B with the `CMD_TLBI_NH_VA` left out (the entry is cleared, the sync is issued). Step 1 showed that QEMU's model then keeps translating from its cache. **Validity condition:** the mutant must change B's outcome; if it does not, B has no power as a control and the experiment says so.

### What is observed, and by what

- Page contents, read by the root task through its own mappings of F, G and O (never through the device).
- The SMMU's event queue after every transfer (type, stream, direction, page).
- The kernel's answers to the capability operations, printed as the kernel gave them (the answer to a copy from a revoked slot, expected `FailedLookup`; the answer to the retype in B; the physical address the kernel reports for G).
- The device's own report that each transfer finished.
- QEMU's trace of its SMMU model (translations, events, invalidation commands), captured with the console as in step 1. It is not independent of the model.

### Hypotheses and what each outcome would mean

- **H-A [Inferred, expected]:** in A the device reads the victim's secret and overwrites G (REACHED). That would be an observation about this arrangement: one task, an unmodified kernel, one SMMU model, a mapping left in place across a revoke. It is the falsifier the [A5 proposal](../../../docs/research/a5-design-proposal.md) describes in its section 4 only in outline: **it is not that test** (no separate donor or server, not K3, not the four A5 tests), and it would not make A5-arm Fail.
- **H-A0 (the surprising outcome):** REFUSED or MIXED. Then something not accounted for (in the kernel, in QEMU's model, or in this experiment) intervenes, and it must be found before anything is concluded.
- **H-B [Inferred, expected]:** REFUSED in B, and the retype attempted while F exists is refused; with the mutant, B is REACHED.
- **H-C [Inferred from the kernel's source, expected]:** the device can read the raw capability. A `CNode_Copy` out of the slot the device wrote is accepted: the kernel links the new copy after that slot and rewrites the back link of slot 1's successor, so the derivation list's forward and backward links disagree (`src/object/cnode.c`, `cteInsert`). Revoking the notification removes slot 1 and the kernel-made copy and repairs that back link (`emptySlot`); the device-written slot and its copy are left **half linked**, pointing into the list but not reachable from the notification, so the revoke does not find them and a signal through the copy still arrives. If the kernel instead halts or faults in C, that is the result, and it is reported as such.

### Stop conditions and limits, fixed in advance

- No criterion is adjusted after a run. If a scenario's positive control fails, the scenario is void and is reported as void.
- If the kernel halts in C, the experiment is not altered to avoid it; A and B stand on their own (C runs last), and the verifier judges them without C.
- **The verifier requires no particular outcome of scenario A or C.** Of B it requires only the validity condition above, that the mutant changes its outcome (a run in which B and the mutant agreed would fail that check, which is how the experiment "says so"). The third review tested this on altered logs: runs with A refused or mixed, and runs that stop inside C, pass; inconsistent runs do not. Two limits it found: a run that stops inside C is accepted without the end-of-run count of unfinished transfers, and a result between the two fixed outcomes is reported as inconsistent in some cases where the design says MIXED. Neither arose. `verify_a5_step2.py` checks that each run is valid, that each printed finding follows from the run's own observation lines by the rule above, that the three boots on a kernel agree, that QEMU's trace is consistent, and that this record states the outcomes the evidence shows. Its checks, the root task and the driver were fixed before the first boot; their hashes are below.
- One emulated SMMU model, one device model, TCG. Nothing here is evidence about hardware, about timing (the device's DMA is synchronous in QEMU; a real device races with the teardown), or about a server that is itself wrong or malicious.
- A result here is a **finding about a naive arrangement and about kernel mechanisms**, not a universal security property and not a verified one. The proof of seL4 "assumes that DMA is off" ([A2a](A2a.md), section 3): everything in this experiment is outside it. Scenario C in particular shows one consequence of a device that can write kernel memory, which is exactly what that assumption excludes; it is not a defect of the kernel.

### Changes the independent review required before the first boot (2026-11-11)

The review's answer was "OK to run after these changes"; all were made before any boot. (1) The verifier had required the expected outcomes; it now requires validity and consistency only, and does not need scenario C to complete. (2) A scenario D ("the untyped held by the server") was dropped: with one task in every role it showed only the kernel rule now noted in B, and its result could have been read as support for an ownership design, which the owner has not chosen. (3) Scenario C's findings were named "forgery"; the device duplicates a capability the task already holds, so they are named duplication, the hypothesis describes the half-linked state the kernel's code leads to, and a kernel-made copy was added as the control for the revocation. (4) The root task now counts transfers the device does not report finished, prints the kernel's answers instead of reducing them to yes or no, and treats an event on a transfer through page O as MIXED. (5) H-A says what would be observed, not what a design does, and names the proposal's falsifier as a different test.

### What was observed [Measured], identically in 3 of 3 boots on the E1-H kernel and on K2R

Every positive control moved 16 of 16 words, and the device reported every transfer finished.

**A. The device reached reused memory.** After the donor's `Revoke` on the untyped, a copy out of the frame's slot and out of the slot of the server's copy were both answered `FailedLookup`: the server's copy of the frame capability went with the original. (The experiment requires this for the scenario to be valid, so it is a condition that held, not an outcome that could have gone either way here.) The kernel then made a new frame from the untyped at the **same physical address**, and it read as zero. With a secret written into it (by the same root task, in its role as victim) and the SMMU mapping never touched, the device **read all 16 words of the secret out** and **overwrote all 16**, and neither transfer left an event record. QEMU's trace reports both as ordinary successful stage-1 translations to that physical address.

**B. With the mapping torn down first, it did not.** The same sequence with the table entry cleared, `CMD_TLBI_NH_VA` and `CMD_SYNC` before the revoke: the device read none of the secret and changed nothing, and each transfer left 16 translation-fault records. On the way, a retype of the untyped attempted while the frame's capability still existed was answered `NotEnoughMemory`. **The mutant** (the entry cleared and the sync issued, but no `CMD_TLBI_NH_VA`) turns B's outcome to REACHED and changes nothing else. So B discriminates, and clearing the entry is not enough in this model: the device goes on using the cached translation. Clearing, invalidating and syncing before the revoke was enough. Invalidating **without** clearing was not tried; by QEMU's code a cache miss walks the table again [Documented: `smmu-common.c`], so it would translate again [Inferred]. Both steps are needed.

**C. Reused as a kernel object, the memory was readable and writable by the device too.** With the untyped retyped into a CNode and a badged notification capability minted into slot 1, the device copied the first two slots out: slot 0 zero, slot 1's four words non-zero, **the badge the root task chose among them** (on E1-H: `360000807000e000 5eedc0de 807ff41bc0 807ff41ba3`; the first is a kernel pointer with the capability's type in its top bits). A `CNode_Copy` out of slot 2 was refused (`FailedLookup`) before the device wrote it and **accepted after the device had copied slot 1's 32 bytes onto it**; a signal through that copy arrived with the badge. After the notification's original capability was revoked, the minted capability and a copy the kernel had made of it were gone (`FailedLookup`), and **a signal through the copy taken from the device-written slot still arrived** (the device-written slot itself, slot 2, cannot be invoked directly and was not). The kernel did not halt in these runs, on the debug or on the release build; nothing in the experiment afterwards exercised the stale list links, on purpose.

### What this shows

- **[Measured] Revoke does not reach the SMMU.** On an unmodified seL4, on a hypervisor-mode debug kernel and on the non-hypervisor 4-node release kernel, a stage-1 translation survives the revocation of the frame it names, and the kernel reuses the memory at once. A device whose stream still has that translation can read and write whatever the memory becomes: here a frame the same task wrote a secret into, and a kernel object. That it would equally be another protection domain's frame is [Inferred]: no second domain was involved.
- **[Measured] A copy of the frame capability did not keep the memory.** The server's copy was deleted by the donor's revoke along with the original (a validity condition of scenario A, which held in every boot).
- **[Measured] "Clear the entry, invalidate, sync, then free" was sufficient here, and without the invalidation it was not** (scenario B and its mutant; step 1's tests 8 and 9). Whether the invalidation alone would be was not tested, and by the model's code it would not.
- **[Measured] A kernel rule:** a retype of the untyped was refused (`NotEnoughMemory`) while a capability to the frame made from it existed. Scenario A shows the limit of that rule: it protects against reuse only until the capability is revoked, and whoever holds the untyped can revoke it.
- **[Measured, with the reading Inferred] Device writes to kernel memory defeat the kernel's bookkeeping, not only its data.** The duplicate in C created no authority the root task lacked. What it shows is that a capability can come to exist that revocation does not find. The mechanism given in H-C (a half-linked entry) is from the kernel's source and was not observed directly.

### What this does not show

- **Not an A5 outcome, and not the proposal's falsifier.** One root task played the server, the donor and the victim and held every capability. Nothing here says what an *untrusted* donor can do to a server in another protection domain: that needs K3, separate capability spaces, and the plan's four tests. A5-arm is neither passed nor failed.
- **Not evidence about hardware or timing.** `edu`'s DMA is synchronous in QEMU, and QEMU completes an invalidation inside the register write. On hardware a device races with the teardown and `CMD_SYNC` takes time; B says nothing about that window.
- **Not a defect of seL4.** Its proofs assume that DMA is off ([A2a](A2a.md), section 3); a device that can write memory is outside them. The finding is about what a system built on it must add.
- **Not a general property.** One model of one SMMU, one device, one stream, one page, two kernel builds.
- The memory layout is the experiment's: a 4 KiB untyped retyped whole. A larger untyped, partial reuse, or reuse by another object type were not tried.

## 3. What would remove the exposure: options, not a decision

The owner has not chosen a design, and this section does not choose one. The constraint every option has to meet is the one A shows: **for every frame a device can reach, whoever can cause that memory to be handed out again must first make the SMMU forget it, and must wait for that.** seL4's revoke is unilateral and immediate and the SMMU's state is outside the kernel, so either the set of parties who can revoke DMA-mapped memory is restricted to parties that follow the protocol, or the kernel takes part. [Inferred] There is no third kind without trusting the revoker; the prior-art note's detection ideas (a revoke canary, leases) narrow the window and cannot close it ([prior art](../../../docs/research/dma-confinement-prior-art.md), O1 and O2).

| Option | What enforces the constraint | Trusted computing base it adds | Correctness argument | Cost |
|---|---|---|---|---|
| **1. Authority shape: a DMA pool** (the prior-art note's O3; the A5 proposal's "ownership design") | Memory a device may reach comes only from untypeds that the SMMU server holds; clients get derived frame capabilities. [Inferred] A client's revoke or delete of its own capability then frees nothing, because the server's capability still exists (the kernel rule noted in B is the fact this rests on; the arrangement itself was not tested), and the server frees only after clear, invalidate and sync | The SMMU server, and **every holder of an ancestor untyped of the pool**: in a static system the initial task that carved the pool. All of it unverified user code, outside the proofs | One invariant in one component ("mapped implies I hold it; freed implies invalidated and synced"), plus a property of the system's capability distribution that can be checked statically: no untrusted subject holds an ancestor of a pool untyped. [Speculative] The initial task could delete its own ancestor capabilities after carving the pool, leaving the server the only authority; whether the kernel's deletion rules allow exactly that was not tested | Clients cannot offer their own memory for DMA: either I/O buffers are allocated from the pool end to end (zero-copy, as statically configured driver frameworks do), or data is copied. Dynamic map and unmap cost an IPC, a table write and an invalidation with its wait; static mappings avoid that on the I/O path |
| **2. Shadow buffers** (copy-based; prior-art note, the ASPLOS 2016 design, secondhand) | As 1, but the device only ever maps server-owned pages that are never unmapped; client data is copied in and out | As 1 | Simplest of all: there is no revoke-while-mapped because nothing mapped is ever reclaimed during operation | One copy per transfer; no invalidation on the I/O path. Measured numbers for this project: none |
| **3. The kernel binds the mapping to the capability** (the plan's K4; how seL4's own SMMUv2 and x86 I/O-space support work) | A mapping exists only through a frame capability; deleting or revoking it makes the kernel unmap and invalidate | An in-kernel SMMUv3 driver: unverified kernel code, and an invalidation wait inside a kernel path | Holds for any distribution of authority, which is its strength. Excluded from the verified configurations; changes the kernel (Class 3 in the plan, not available under the present policy) | The wait for `CMD_SYNC` on hardware is not bounded by the kernel; it would sit in revoke, which bears on worst-case kernel latency. Not measured |
| **4. The kernel only defers reuse** [Speculative; no prior art found in this project's notes for seL4] | No driver in the kernel. A frame can be marked pinned by a holder; revoke still removes every capability, but the untyped is not handed out again until the pin holder acknowledges | A small kernel change (a check on the retype path and a notification), which would need its own proof work, and the SMMU server | Keeps revoke unilateral for authority and makes only *reuse* wait. A pin holder that never acknowledges holds the memory, so it must be trusted or bounded by quota | One notification and one acknowledgement per reclaimed frame. Also a kernel change, so also Class 3 |

[Inferred] Options 1 and 2 are the only ones available without a kernel change, and both put the SMMU server and the root of the pool's authority into the trusted base for P5, which the plan's P5 cell must then list (label S). Option 3 is the only one that tolerates an arbitrary distribution of authority. None was built or measured here.

**A falsifiable next experiment** (not authorized, proposed; it presupposes that the owner picks an option, and is described for options 1 and 2 only because they need no kernel change under the present policy, not because either is preferred): K3 proper on K2 and K2R. The SMMU driver of step 1 becomes a server task with its own capability space; a client task in another capability space is given derived frame capabilities and no ancestor; the client then does everything it can (delete, revoke, exit while a transfer is armed) and the four A5 tests are run with their mutants. Falsified if any client action leads to a device transfer reaching memory the kernel has handed to someone else. Step 2's scenario A is the positive control that such a test must be able to reproduce when the client *is* given the ancestor.
