# K3: a user-level SMMUv3 server in its own protection domain (A5-arm)

**Status: design, revised after an independent design review and fixed before the evidence run.** The result section (9) is filled in after
the run. Authorized by the owner's message of 2026-11-11 ("Implement and execute the K3 experiment ... Execute the four required A5
tests and appropriate adversarial controls. Follow the recorded acceptance criteria without silently changing them", and that the
agent decide the design technically). It changes no kernel, loader, dependency, ADR or CI. Labels as in AGENTS.md. Everything runs under
QEMU TCG; nothing here is evidence about hardware.

**How this record came about, stated so it can be judged.** The first version of this design (before any code) was reviewed by the `reviewer`
agent, which found three blockers and several weaknesses (section 10 lists them and what was done). Code was written in parallel and
run during development, on K2 and K2R, which changed the experiment in these ways, none of them to a recorded criterion: two harness bugs
(a receive-slot clash; type-probing endpoint capabilities by invocation, which is an IPC) were fixed; a first observation rule (a refused read
leaves the marker) was wrong and replaced by the one in section 6 after the reviewer pointed to what step 1 had measured; one mutant
(`shared-asid`) had no effect under the first test and a reverse-direction test (T1g) was added; and the sets of collateral failures in section 7
are the ones seen in development. The evidence run (section 9) uses the sources whose hashes are listed in section 8. **The evidence was recorded six times** (the first for a checker error, the second for a weak self-test corruption, the third for the second review's findings, the fourth for a bug those fixes introduced, the fifth for the delta review's findings, the sixth for a unit error in the new per-stream check, which a development boot without QEMU's trace could not show). The first run's results were the same, but judging it with `verify_k3.py` exposed two errors in the checker and build script (a boot count of 22 for 20, and an assumption that the client binary is byte-identical across variants, which is false when each variant is built in its own directory because the path is embedded in the binary); both were corrected and the whole run repeated. The second independent review (of the code and the evidence) found that the checker re-judged too little (it still passed when observations were edited), that one test printed `MIXED` for every observation because a secret pattern of base 0 has a zero word, that a few claims had no test that could fail, and some smaller defects (section 10b); all were fixed and the run repeated. The raw logs of the run before the last are kept locally and are not evidence.

## 1. Question and the plan's wording

[Plan, A5-arm] "Run a negative test with `-machine virt,iommu=smmuv3`: a device must reach only its mapped region, and DMA outside it must fault and be
reported. Run a teardown-ordering test: after a mapping is torn down and its memory reused, device DMA to it must fault." **Pass:** "K3 passes all four P5
tests with no kernel change, and teardown provably blocks device access before memory is reused, shown by the revoke-while-mapped and driver-killed tests."
**Fail:** "a device reached memory outside its mapping, or DMA into reclaimed memory succeeded, or the only working option needs a Class 3 change or a change
that was not approved first." [Plan, P5 row] the four tests are the negative test, cooperative teardown, revoke-while-mapped ("memory reclaimed by revoke while the
SMMU server still maps it") and driver-killed ("driver killed during DMA"). [A5 proposal, section 4] "*If the DMA changes the reused memory, A5-arm is Fail under K3 with no kernel change.* If the design makes the reclaim impossible for an untrusted
donor, "the same test must show that the donor's revoke does not return the memory, and the claim becomes: *confinement holds against untrusted donors, and the root
task is in the trusted base*." The proposal also records the expectation that "the naive design (the donor keeps the parent capability) [fails] step 3, and the ownership design [survives] it at the price of putting the root task in the P5 trusted base". The control N is that naive design: read literally, the first sentence is satisfied by N, which is why N is declared not to be K3 (below) and why the owner's acceptance of that reading is requested.

**How each test is interpreted here (an interpretation, to be accepted or rejected by the owner with the result):**
- *Negative test:* T1. *Cooperative teardown:* T2.
- *Revoke-while-mapped:* in this design nobody untrusted can reclaim mapped memory, so the test has two halves. (a) T3a: every untrusted party tries to reclaim a
  page the server still maps and the kernel's answers show the memory was not reclaimed. (b) T3c: the *same actions* (a donor's memory is reclaimed by the memory
  manager and reused) are run against a server that accepts donations (the control N) and against the design. **In the design build T3c has no discriminating power of its own**: the donation is refused, so nothing is mapped for the reclaimed memory and the later reads are refused for the same reason as in T1b; what discriminates is N against the design, the kernel probe of T3a and the mutant. The failing version (a server that reclaims while
  mapped) is the mutant `reclaim-while-mapped`.
- *Driver killed during DMA:* T4. `edu` runs its DMA about 100 ms after the trigger, so a driver can really be killed while its transfer is in flight.
- *The control N is not K3.* It is a deliberately unsafe server, like a mutant. Its REACHED is not an A5-arm Fail under the plan's wording ("DMA into reclaimed memory
  succeeded" is read as a statement about the configuration under test); this reading is the owner's to accept. N differs from the design build by one flag:
  the server sets a receive slot and maps a donated frame. In both builds M's endpoint capability has the Grant right and the same message is sent.

## 2. The design under test

**A DMA pool whose ancestors nobody untrusted holds.** In seL4 whoever holds an ancestor of an untyped can revoke it ([A5 step 2](A5-step2.md) scenario A measured this
for the holder of the untyped itself; that it holds for every ancestor follows from the kernel's derivation rules [Documented: `cnode.c`, `cteRevoke`, `isMDBParentOf`]).
So P5 is a statement about the authority graph:

> **I1.** Every physical page a device stream can reach, *and every page the SMMU itself reads or writes (stream table, queues, translation tables, context
> descriptors)*, is a child of a boot untyped that was *moved* into the server's CNode: it has no ancestor, and nobody but the server's CNode holds a capability to it.
> **I2.** The server frees a pool page only in this order: clear the translation, invalidate it, wait for the SMMU (`CMD_SYNC`), then revoke the page's untyped.
> **I3.** A client obtains CPU access to pool memory only as a *copy of the server's frame capability*, delivered by the reply of a call; a client's delete, revoke,
> unmap or death frees nothing, and the server can always take the memory back (a revoke of the page's untyped removes every copy) [Documented: `thread.c` transfer, `cnode.c`].

**Trusted base for P5 [Inferred; tested only as far as section 5 says]:** the kernel; the SMMU server; the elfloader that starts the kernel and root task (an unlisted trusted component
is class D in the plan's matrix, so it is listed); and **the root task as the initial task**. The root task is trusted *with respect to the pool and the SMMU*: it holds
the CNode, TCB and VSpace capabilities of the server and could revoke, retype or delete anything in it. It also holds the memory-management role for M's memory.
**What the experiment tests is therefore narrower than "an untrusted memory manager":** it tests clients and a memory owner (M) that are hostile, and shows that reclaiming and reusing the untyped *the memory manager gave M* does not touch the pool or the SMMU's memory, which is disjoint from it by construction. The root task is one CSpace: it also holds S's CNode, and it maps the SMMU's register pages itself (the device mapper does, and S receives copies). **A hostile or buggy root task is outside the claim, and no test here could fail it.**
Not trusted: clients C1 and C2, the memory owner M. Not covered: hardware; a faulty or malicious *device* (an SMMU stream isolates devices from each other and from memory; it does not make one
device's own mapped buffer safe); timing; the server's own bugs (the mutants are deliberate ones).

**The price, stated in advance:** a device can DMA only into pool pages. No zero-copy from arbitrary client memory; a client copies, or allocates its I/O buffers from the pool.

**Rejected for K3 and why.** Donated memory (a client or the memory manager gives the server its own frames): kept only as control N. Kernel binding or deferral of reuse (options 3 and 4 of A5 step 2): Class 3 under the plan's Kernel modification
policy; researched separately in `docs/research/dma-ownership-architecture.md` and cannot make A5-arm a Pass.

## 3. Domains and capabilities

Five protection domains, each with its own CNode and VSpace, started by the root task. Each task has a *CNode capability to itself* and a *VSpace capability to itself* (so a client can delete, revoke, copy, mint, map and unmap within its own CSpace and address space).
No task holds a TCB capability, an IRQ or ASID capability, or a capability to another task's CNode or VSpace. The seed table (every capability placed, with its kind: copy, mint or move) is printed by every run (`K3 seed`), and the verifier checks it.

| Domain | Role | Holds besides its own CNode and VSpace | Trusted for P5 |
|---|---|---|---|
| **R** root task | creates domains; conductor; oracle; memory manager for M | everything it did not move away; **not** `U_pool` or `U_srv` (moved to S) | yes (initial task) |
| **S** server | owns the SMMU and the pool | the two SMMU register frames; `U_srv`; `U_pool`; the receive end of its endpoint; a send capability to R's endpoint (used once, only if set-up fails) | yes |
| **C1**, **C2** | untrusted drivers, each driving one `edu` | a badged send capability (write, grant) to S; the BAR frame of its own `edu`; a badged send capability to R's endpoint; its step notification | no |
| **M** | untrusted memory owner (donor, victim of reuse) | a badged send capability (write, grant) to S; `U_M`, a *copy* of an untyped R keeps; R's endpoint; its step notification | no |

Badges on S's endpoint cannot be forged: a badged endpoint capability cannot be re-badged [Documented: `cnode.c`, `objecttype.c`] (T3a2 tests it). R's own capability has the admin badge.

## 4. Protocol and teardown

Pool page *i* (8 pages): a 4 KiB untyped `U_i` (child of `U_pool`, held by S) and, when allocated, the frame `F_i` retyped from it; owner; I/O address in the owner's address space. One SMMU address space per client (own three tables, context descriptor, ASID).
`ALLOC` (reply carries a copy of `F_i`), `FREE(handle)` (owner only), admin: `BIND`, `DEAD(client)`, `EVENTS`, `STATS`, `PAGEINFO`, `SMMU_PA`, `PROBE`. Anything else, and every admin operation from a client, is refused. The design build sets no receive slot, so a capability sent to S is dropped by the kernel.
Teardown = clear the entry, `CMD_TLBI_NH_VA`, `CMD_SYNC`, revoke `U_i`, mark free. Resource cost is counted (SMMU commands, syncs, revokes per operation) because timing under TCG means nothing.

## 5. Tests (a test passes only when every listed sub-check holds; a precondition that fails makes it VOID, never a pass)

Observation primitives. `leak(t)`: the attacker's device reads 64 bytes from bus address `t` into its buffer and writes the buffer to its own page. **QEMU's SMMU model leaves the device's buffer zero when a read is refused** ([Measured], A5 step 1), so: REACHED = all 16 words of the target's secret arrived; REFUSED = all 16 words zero *and* at least one fault record for the attacker's stream; anything else MIXED. `clobber(t)`: the device writes the attack pattern to `t`; the target's owner counts its words: REACHED = all 16 overwritten, INTACT = none. The event queue is drained around every transfer and a run is invalid if the SMMU reports an overflow; the number of records the server read must equal the number QEMU's trace reports pushing.

- **T1 Negative test.** (a) positive control: the device moves C1's page into C1's other page. (b) a read of an unmapped I/O address: REFUSED. (c) reads at the *physical* addresses of C2's page and M's page: REFUSED; (c3) at the physical address of the SMMU's stream table entry for C1's stream, of the command queue and of a level-1 table (all non-zero): REFUSED. (g) after C1 and C2 have used the same I/O address, C2's device reads C2's own page (a cache keyed by something shared would serve it C1's). (d) C1 reads the I/O address that C2's page has in C2's space: C1 gets its own data, never C2's. (e) writes to those targets: C2's and M's pages INTACT, faults recorded where the target is unmapped. (f) C2 cannot free C1's page.
- **T2 Cooperative teardown.** After C1 frees a page: its old I/O address is REFUSED; C1's capability to the frame is gone; C2 is given the same physical page; C1 cannot free it (the handle is now C2's); C1's `leak` and `clobber` through the old address are REFUSED and INTACT.
- **T3 Revoke-while-mapped.** (a) C1 holds a mapped page and does everything it can to its own CSpace (copy, revoke, `Untyped_Retype` and `TCB_Suspend` on every slot that is not an endpoint, notification or its own CNode/VSpace; re-badging; admin calls; unmap and map; revoke and delete of its frame capability); the page stays mapped and reachable by the device; **the kernel still gives the frame's address to the server and refuses to retype the page's untyped (`NotEnoughMemory`)**; the rest of the pool is taken and no page is handed out twice; M holds exactly one untyped (its own). (c) M offers a frame; the memory manager revokes M's untyped and gives the memory to C2; C1's device tries the offered address and the physical address. Design: donation refused, REFUSED/INTACT. Control N: positive control REACHED first, then REACHED/REACHED.
- **T4 Driver killed during DMA.** C1 starts a transfer (the timer will run it ~100 ms later) and is suspended at once; the server is told; C2 is given C1's physical page and writes a secret; the transfer then runs: it must fault and C2's page must be INTACT. The run bit of the device must still be set at the kill, after the teardown and when C2 owns the page, or the sub-check is VOID. The root-task-started transfer (T4pre, with the mapping alive, must land; T4c, after the death, must fault) is a control for the mechanism.

## 6. Outcome rule for A5-arm (the plan's, applied; not changed)

- **Pass:** on K2 *and* K2R, in 3 of 3 boots, every sub-check passes in the design build; the control reproduces REACHED; each mutant breaks the sub-checks predicted for it; no kernel, loader or dependency changed.
  The claim is then: *confinement holds against untrusted clients and an untrusted memory owner whose memory the memory manager reclaims, with the SMMU server, the initial task (all of it), the elfloader and the kernel in the trusted base and DMA memory coming only from the pool.*
- **Fail:** in the design build a device reached memory outside its mapping or DMA into reclaimed memory succeeded; or (**a clause this record adds to test the design's own invariant I1, not a criterion of the plan**) an untrusted domain was found to hold an untyped that is, or is an ancestor of, pool or SMMU memory. M's `U_M` is such an untyped only if it overlaps the pool, which the boot untyped list excludes.
- **Investigate:** a sub-check did not run, was void, or its result is ambiguous; a mutant had no effect.
- The control's REACHED is not an A5-arm Fail (section 1).

## 9. Results

**The agent's measurement, not an accepted outcome.** Run on 2026-11-11 with the sources of section 8, on K2 (debug, non-hypervisor, 4 vCPUs) and K2R (release), seL4's elfloader, QEMU 11.1.3 TCG, `virt,iommu=smmuv3,highmem=off`, two `edu` devices. Twenty boots per recording (per kernel: 3 design, 1 naive control, 6 mutants), all launched and judged by
`verify_k3.py` (its checks are listed in `verify-evidence.py`; procedure: `run-k3-evidence.sh`, `sanitize-run.py K3`, `verify-evidence.py`). The outcomes the evidence shows, which the checker requires to be stated here word for word:

- `K2: design passes 36 of 36 checks in 3 of 3 boots; naive control passes its 37 checks, reproducing REACHED; mutants: skip-invalidate fails T2a,T2d,T3a4,T3pre,T4b,T4c; reclaim-while-mapped fails T2a,T2d,T3a4,T3pre,T4b,T4c; no-owner-check fails T1f,T2e; death-without-teardown fails T4b,T4c; shared-address-space fails T1d,T1e,T2d,T4b,T4c; shared-asid fails T1g`
- `K2R: design passes 36 of 36 checks in 3 of 3 boots; naive control passes its 37 checks, reproducing REACHED; mutants: skip-invalidate fails T2a,T2d,T3a4,T3pre,T4b,T4c; reclaim-while-mapped fails T2a,T2d,T3a4,T3pre,T4b,T4c; no-owner-check fails T1f,T2e; death-without-teardown fails T4b,T4c; shared-address-space fails T1d,T1e,T2d,T4b,T4c; shared-asid fails T1g`

("Checks" counts the `K3 test` lines: 36 in a design boot, 35 distinct ids, because `S0d` is reported once per client.)

### What was observed [Measured], identically on K2 and K2R

- **The design held in every design boot** (3 per kernel, 6 in all): all 36 check lines passed, none void. Every refused transfer left a zero buffer and 16 fault records for the attacker's stream; the number of event records the server read (272 per design boot) equals the number QEMU's SMMU model reports pushing, so the server neither hid nor invented a fault.
- **Authority.** C1 and C2 started with 7 capabilities each (their CNode and VSpace, the three common endpoints and notification, the server endpoint, their own device frame): no untyped, one frame. In T3a, C1's own sweep of its CSpace found the same 10 capabilities and 4 frames (its device and three pool pages) that the root task found by copying every slot. An `Untyped_Retype` or `TCB_Suspend` on every slot that is not an endpoint, notification or its own CNode or VSpace failed. A `Revoke` on every slot succeeded (0 failures; M's own untyped is left out of that sweep because its frames are its children). It could not use the admin calls or re-badge its endpoint capability.
- **Revoke-while-mapped, design.** After C1 revoked and deleted its own capability to a mapped page, the page stayed mapped and reachable by the device; the kernel still answered for the frame's address and refused to retype the page's untyped (`NotEnoughMemory`); for a *freed* page the kernel had no frame to answer for and accepted the retype (the control for that probe); with the pool used up no page was handed out twice. A donation was refused and kept no capability. **The design half of T3c has no discriminating power of its own** (nothing was mapped for the reclaimed memory, so the later reads fail as in T1b); the discrimination is the control N against the design, the kernel probe, and the mutants.
- **Cooperative teardown and driver death.** After a free, the old I/O address faulted, the capability was gone, and the reused page (same physical address, from each side's own `frame_get_address`) was untouched by C1's device. A transfer *running* when its driver was killed (the device's run bit was set at the kill, after the teardown, and when C2 owned the page) faulted with 16 records and left C2's page intact; started again later, it faulted again. **Only the driver's TCB was suspended**; its CNode and VSpace were not destroyed.
- **Control N.** The server that accepts donations reproduced the A5 step 2 falsifier across protection domains: the device read the donated memory (positive control), and after the memory manager reclaimed it and gave it to C2, C1's device read all 16 words of C2's secret and overwrote all 16, with no fault.
- **Mutants.** Each of the six server bugs was detected on both kernels, with the sub-check sets of section 7. `skip-invalidate` and `reclaim-while-mapped` fail the same six checks, because they leave the cached translation or the table entry and the same teardown is used by T4 and by the reuse of an I/O address in T3. `shared-asid` is detected by T1g only: with one ASID for two streams, C2's round trip read back its *old* words (16 of 16), so none of its own data arrived. That the write landed in C1's page is [Inferred]; it was not checked.
- **Structural cost** (counts, not timings): `ALLOC` issues 0 SMMU commands; `FREE` issues 2 commands (page invalidation and sync), waits for 1 sync and does 1 revoke; a whole run of 15 allocations used 25 commands, 11 syncs, 8 revokes.

### Against the outcome rule (section 6), the agent's reading

Every Pass condition holds in this evidence: 3 of 3 boots on each kernel, all sub-checks of the design build pass, the control reproduces REACHED, each mutant breaks what was predicted, no kernel, loader or dependency changed. **That is not a decision.** Three things stand between it and an outcome: (1) the owner has not accepted the interpretation of section 1 (the revoke-while-mapped test in a design where nothing untrusted can reclaim, and the control's status); (2) the claim is narrower than "DMA is confined": it holds for this arrangement of authority, one emulated model, an unmodified kernel, with the server, the whole initial task, the elfloader and the kernel in the trusted base (section 2) and with the gaps of section 11; (3) the evidence was recorded six times and the checker was strengthened between recordings (sections 10b and 10c), so its independence from the code under test rests on the review of the final state, which is requested.

### What the development runs taught

The mechanism passed on the first complete boot; what took effort was the experiment. An `Untyped_Retype` probe on a copy of an endpoint capability is an IPC (it made the root task call itself), so type-probing a CSpace by invocation is unsafe and the sweep skips the communication slots. A refused read leaves a zero buffer, not the marker. The `edu` timer makes a true in-flight kill possible. A `Revoke` sweep over an untyped holder's own slots destroys its own frames, which silently emptied a donation in the control (the design build masked it by refusing donations anyway; the checker's re-derivation of the control found it).

### 10c. The delta review, and the checker's limits

The delta review (of the final code, the evidence and this record) found the fixes of 10b real, found the trust statement honest, and found the claims of section 9 that it checked derivable from the logs. It also showed, by editing copies of the evidence, that 17 of 23 targeted corruptions still passed the checker: it re-derived the decisive verdicts but took some from the root task, and it did not tie the numbers on `K3 obs` lines back to the raw `K3 rep` and `K3 adm` lines they come from. **What was done:** T2b, T1e0, T3a6, S0d and the identification of T3a7's page are now re-derived, T3a8's handle is tied to T3a5's mask, and the event records are compared **per stream** with QEMU's trace (the server's counts for C1's, C2's and other streams against the records QEMU pushed for each stream id). **What was not done, and is therefore a stated limit:** the `obs` lines are the root task's reduction of what the tasks and the server reported, and the checker does not recompute them from the raw lines; T1pre, T2free and T3c1's target are not re-derived; the cost lines are not tied to the server's STATS replies. A reader who wants the stronger claim needs a checker that parses the raw reports.

## 11. What this does not show

One emulated SMMU model and one device model. QEMU completes an invalidation inside the register write; a real device races with the teardown, `CMD_SYNC` has real latency, and a real device needs a quiesce step (bus-master disable, function reset) before the pages are freed: the server's interface has a place for it and this experiment cannot test it.
The 100 ms timer of `edu` is real, but a hardware device's in-flight DMA is not bounded by one timer. The server, the root task and every client are unverified; seL4's proofs assume DMA is off ([A2a](A2a.md)). Not tested: the death of a client whose CNode and VSpace are destroyed; a client killed while blocked in `ALLOC`; request flooding beyond
`ALLOC` returning an error at pool exhaustion; more than two streams; a second SMMU; the ASID-reuse behaviour of real hardware; a hostile root task.
