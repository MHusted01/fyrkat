# E3: capability revocation, with a surviving ancestor and an unrelated control

**Outcome (agent's reading): Pass, label U, functional only.** After a root task called `seL4_CNode_Revoke` on its capability `P`
to an endpoint, the badged mints of `P` and a copy of each mint, held in the CNodes of two separate tasks, were gone: the root task could
no longer copy them, the tasks' calls through them were refused by the kernel, and nothing reached the root task through them. `P`
itself, an unrelated endpoint `Q` with the tasks' mints of it, and a new mint of `P` made after the revoke all still worked.
3 of 3 boots under QEMU 11.1.3 TCG on the E1-H kernel configuration [Measured: [E3/10-boot-1..3](E3/)]. Six mutants fail as they
should. **The owner finally accepted it as Pass (U), limited to the tested capability-revocation topology under single-vCPU QEMU TCG with the debug kernel** (2026-11-09), after two independent reviews: the first returned NOT MERGE-READY, its findings were addressed and the evidence was rerun, and the second, of the final evidence, returned **MERGE-READY** with no material finding.
The acceptance keeps the limitations below, and they must not be represented as independently reviewed or production-ready: the verifier was tightened **after** the second review (not reviewed), forged-log gaps remain, and one `SAFETY` comment is inaccurate. It is not Stage B, P1 or P2 evidence
(A2a has not run), and says nothing about HVF, SMP, hardware, performance, timing, side channels, or the formal assurance of seL4's revocation.

verifier and sanitizer (D22). `Cargo.toml` and `Cargo.lock` are unchanged. No kernel, loader or `crates/root-task` source changed. No E2 source file changed except that `crates/e2-task/src/lib.rs` gained one line

## What the system does

The root task retypes two endpoints, `P` (the **ancestor**: the capability that `Revoke` is called on) and `Q` (a control that `P` has nothing to do
with), and three notifications. It builds two identical tasks (ids 1 and 2), each with its own address space, CNode, TCB and IPC buffer, and
**no capability to its own CNode** (so only the root task can empty one of its slots) and no fault handler (so nothing it does reaches the root
task through a fault). Each task's CNode holds:

| Slot | Content | Derivation |
|---|---|---|
| 1 `DERIVED` | mint of `P`, badge `0xb30<id>`, write and grant-reply | child of `P` |
| 2 `COPY` | copy of slot 1, made by the root task | descendant of `P`: it is not itself revocable, but `P` has badge 0, so `P` is its parent in the kernel's sense [Documented: `isMDBParentOf`, `src/object/cnode.c`, `isCapRevocable`, `src/object/objecttype.c`, at the pinned seL4 commit] |
| 3 `CONTROL` | mint of `Q`, badge `0xd30<id>` | child of `Q`; `P` is not its ancestor |
| 4, 5 | the task's go-signal (read-only notification) and its event signal to the root task (write-only, badged) | unrelated |
| 6 `EMPTY` | never populated | negative control |
| 7 `FRESH` | empty until after the revoke; then a new mint of `P`, badge `0xf30<id>` | child of `P`, made after the revoke |

The kernel's `cteRevoke` deletes the run of capabilities that follow `P` in its derivation list and for which `P` is the parent; each mint and copy is inserted directly after its source, so the four
caps of slots 1 and 2 are that run, and `Q`'s mints are not (a different object) [Documented, and checked by the independent reviewer against the pinned source].

The root task drives the run with signals, so the order is the same in every boot (one CPU; the tasks have the lowest priority and run only
when the root task blocks). The event notification is bound to the root task's TCB, so a task's signal wakes the root task even
while it waits on `P`; a call that did get through `P` would arrive there first.

| Step | Observed (identical in all three boots) |
|---|---|
| Before: populated | The root task copies each of slots 1, 2 and 3 of both tasks into a scratch slot of its own CNode (each succeeds, and the copy is deleted again). The same for `P` |
| Before: usable | Each task calls through slot 1, slot 2 and slot 3 in turn. The root task receives each call with the badge the kernel attached (`0xb301`, `0xb301`, `0xd301`; then `0xb302`, `0xb302`, `0xd302`) and answers it; the task checks the answer |
| Before: negative controls | The root-side copy from slots 6 and 7 is refused (`FailedLookup`) |
| Revoke | `E3_ROOT revoke step`, `E3_ROOT revoke P`: `root_cnode.absolute_cptr(P).revoke()` returns success. `P` is the original capability from the retype, held in the root task's CNode |
| After: gone | The root-side copy from slots 1, 2, 6 and 7 of both tasks is refused (`FailedLookup`); the same from slot 3 succeeds. Copies of `P` and `Q` in the root task's CNode succeed |
| After: refused | Each task calls through slot 1, slot 2 and slot 6. All three are refused at once with reply label `2` (`InvalidCapability`), and the kernel logs `Attempted to invoke a null cap #1`, `#2`, `#6` once per task. The task then signals; **that signal is the first thing to reach the root task**: no call through a derived capability arrived on `P` |
| After: control | Each task calls through slot 3 and is served (badge `0xd301`, `0xd302`) |
| After: ancestor | The root task mints a new child of `P` into slot 7 of each task (success, and it is populated). Each task calls through it; the root task receives it on `P` with badge `0xf301` and `0xf302`. Then `E3_PASS` |

Also stated by the verifier: no `E3_FAIL`, panic, halt, assertion, abort, exception or "fault" in any guest log; the output through `E3_PASS` is identical across the three boots (the three logs are

## The error behaviour, observed

[Measured, 3 of 3 boots] After the revoke, a `Call` through a revoked slot (slot 1 or 2) returns the reply label `2` (`InvalidCapability`). **So does a call through slot 6, which was never populated.**
A root-side `Copy` from a revoked slot and from a never-populated slot both fail with `FailedLookup`. The kernel logs the same line for both calls (`Attempted to invoke a null cap`) and the same
line for both copies (`Source slot invalid or empty`). So the error code **does not distinguish a revoked slot from a never-populated one** here, and this record does not rely on it: the evidence is the
before/after pair on the same slot, the surviving ancestor and control, and the mutants. That the codes are equal is an observation of this kernel and call path; the API does not promise it either way.
The verifier requires a non-zero label on the tasks' side (it accepts any, not only `2`), and `FailedLookup` on the root's side for every refused copy, because that is what the log shows and a different error there would mean a different failure.

## Do the tests detect failure? (six mutants)

`build-e3.sh --mutant NAME` rebuilds only the root task (with the compile-time variable `E3_MUTANT`, unset in the evidence build) and the image, against the **evidence build's kernel, loader and
task binary, byte for byte**. No source file was edited. Each mutant's log says what the root task did instead of the revoke (`E3_ROOT mutant: ...`). [Measured: [06](E3/06-mutation-checks.txt)]

| Mutant | Meant to reach | Observed |
|---|---|---|
| M1 `noop-revoke`: no revoke | the root-side probe of a slot that should be empty | Every step before the revoke passes. The probe of task 1's slot 1 finds it populated: `E3_FAIL root: Check("a slot that should be empty is populated")` |
| M2 `revoke-wrong-ancestor`: `Revoke` on `Q` | the same, for the wrong ancestor | The same stop: `P`'s mint survived. That `Q`'s mints were removed was **not observed here** (slot 3 is never probed once the run stops); it is [Inferred] from the kernel source, and M4 observes it |
| M3 `noop-revoke-blind-probes`: no revoke, and the probes of slots 1 and 2 after it left out | a call through a derived capability reaching the root task | Task 1's call through slot 1 reaches the root task (`call reached the root task: badge=0xb301 code=0x400`): `E3_FAIL root: Check("a call arrived where the task's event was due")` |
| M4 `revoke-too-much`: `Revoke` on `P`, then on `Q` | the check that the control stays populated (selectivity) | Task 1's slots 1 and 2 are refused, as they should be; then the probe of slot 3 finds it empty: `copy refused (FailedLookup), but the slot should be populated`, `E3_FAIL root: Check("a slot that should be populated is empty")`. This also observes that a revoke of `Q` removes a mint of `Q` (task 1's, the only one probed) |
| M5 `revoke-task-1-only`: task 1's slots 1 and 2 deleted, no revoke | the checks on task 2 (the second CNode) | Task 1's whole after-phase passes (its slots refused, its control served); then task 2's probe finds slot 1 still populated: `E3_FAIL root: Check("a slot that should be empty is populated")`. So a removal that reaches only one task's CNode is seen, which is the point of requirement 6 |
| M6 `serve-refused`: no revoke, probes left out, and the root task answers the call | the task's own refusal check | The root answers task 1's call through slot 1 (label 0); the **task** prints `E3_FAIL task: a call that should be refused was served`, and the run never reaches `E3_PASS` (it waits for a task that has stopped) |

With M3 and M6 the root-side probe is out of the way, so what fails is a different detector; with M1, M2, M4 and M5 the probe fails first. I did not build a mutant that makes the *kernel* refuse a call that should work, or one that revokes late, or only part of the derived capabilities inside the kernel, or from a different but related capability (M5 removes two slots by deletion, which is not a partial revoke).

## Limitations

- **Debug kernel**, non-MCS, one vCPU, TCG only, half the RAM of A1, no hardware. As in E2, `seL4_DebugPutChar` is not mediated by a capability.
- **One revoke topology.** `P` is a retype-original, unbadged endpoint capability; its children are badged mints and a same-badge copy. Not tested: revoking a badged child (which would remove only its same-badge
  copies), revoking an untyped (which destroys objects), a deeper chain, revocation with a thread blocked on the endpoint, notification or other object types, a revoke that is preempted, a revoke by a task, or a second revoke.
- **Symmetry.** The two tasks are identical, so "server" and "client" are not different roles here. The `COPY` slot is a copy of the same task's mint, made by the root task, not of the other task's. The recommendation the owner authorized had the
  server send on its derived capability and an optional copy in the client's CNode; this experiment uses `Call` (so that a refusal is visible as a reply label; a refused `Send` is silent), gives both tasks a mint and a copy, and adds a mint after the revoke.
- **Same badge on slots 1 and 2.** A copy keeps its badge, so the root task tells slot 1 from slot 2 by the code in the task's message, not by the kernel-attached badge [Inferred: the task's source sends the
  code for the slot it uses].
- **The root-side probe is a `Copy`.** It shows that a slot holds or does not hold a capability; it does not show which type. Whether the surviving capabilities are the *same* ones as before rests on the slot
  and the badge, not on an object identity check.
- **Whether the refusal is "because of the revoke"** rests on three things together: the same slot was populated and served before and is empty after, the tasks hold no capability to a CNode and so cannot
  have emptied it, and the mutants without a revoke leave it populated. It is not read from any kernel state.
- **Mutants are not exhaustive** (see above).
- **Verifier gaps that remain** [Measured by the reviewer, who altered copies of the evidence]: each needs a forged or inconsistent log, which the verifier cannot rule out because it reads the program's own output. Examples that still pass: kernel lines removed from a mutant section after the revoke
  (only the four before it are counted); M5 with task 1's refusal lines removed, or M4 with its slot 2, 6 and 7 probe lines removed; M2's pre-revoke probe lines removed; an extra `recv on P` line after M1's stop; a refusal label of 99 (accepted on purpose); the free-text header of `06-mutation-checks.txt`.
  The null-cap lines' thread attribution and the order of a mutant's stop and failure lines are now checked.
- **The source and script hashes are pinned.** The verifier compares the recorded SHA-256 of `build-e2.sh`, `boot-image.py`, `lib.rs` and the E3 files with the files in the repository, so a later edit to any of them makes the E3 check fail until the evidence is re-recorded or the exception is recorded. That is the intent.
  The driver `run-e3-evidence.sh` is not among the hashed files.
- **The scratch slot** of the root task's CNode (the last empty one, used for the probing copies) is not reserved from the allocator. A collision would make a probe fail, so it fails closed.
- **`unsafe`.** The E3 code has no `unsafe` block. `e3_spawn.rs` has an `unsafe extern "C"` declaration of the linker symbol `__executable_start` (now declared as `u8`; only its address is taken) and a `static mut` page placeholder, both copied from
  E2 and from upstream's `spawn-task` example. Both now carry a `SAFETY` comment. The reviewer measured that the symbol is the image's first load address (`0x200000`) and that the placeholder is one page-aligned page of `.bss`; the root task is a single thread; the placeholder is only used through `addr_of!`. The spike workspace
  is outside the root workspace lints, so `undocumented_unsafe_blocks` is not enforced there, and clippy is not installed for the pinned nightly, so it was not run. A safer alternative needs the allocator or the frame to be reachable without the symbol; it was not attempted. **One imprecision, left as is because editing the file would invalidate the recorded source hash:** the `SAFETY` comment on the `static mut` says it is "never read or written"; `map_image` in `child_vspace.rs` writes at its address after the frame has been replaced, which is why it is `static mut`. The physical page behind the static is never touched, so it is not a soundness problem, and the write is covered by that function's own `SAFETY` comment. Also left as is: the M5 arm of `revoke` indexes `sys.tasks[0]`, a panic path in non-test code that is compiled but dead in the evidence binary.
- **Superseded runs.** Three runs came before this one, kept locally and gitignored (`external/e3-superseded-first-run/`, `external/e3-superseded-second-run/`, `results-raw/E3-superseded-*`): a first build attempt that failed on an unexported variable in `build-e3.sh`; a first complete run with two mutants
  whose task binary was rebuilt per mutant (a different hash, from the build directory); and the second complete run, with three mutants, which the first review examined. The final run was made from the final source after the review's changes.
- **Warnings.** The kernel link warns that `kernel.elf` has an RWX segment, and the GIC target-ID warning appears, both as in E1 and E2.
