# C2 method: page faults against Linux

- **Status:** Draft for owner review. No run of C2 has happened, pilot or otherwise.
- **Plan:** [seL4 feasibility spike plan](../../../docs/research/sel4-spike-plan.md), experiment C2,
  approved at `46a90fa`.
- **Effect:** the plan requires this file to be committed before any C2 run. Once committed on
  `main`, changing it after the first run is an Amendment to the plan. Every C2 results file
  cites the commit SHA of this file as it exists on `main`.
- **Pilot rule:** a pilot may check that the harness works. Its numbers are not recorded as
  results and may not change this method.

This file fixes the method. It does not change any criterion.

## Criterion

From the plan, unchanged:

- **Pass:** every workload is within 3 times Linux.
- **Investigate:** any workload is above 3 times. Record the cause and any identified fix. Above 5
  times, profile as well, and record whether the cost is inherent to the design, to the user-level
  pager, or to the virtualized setup.

3 times and 5 times are investigation thresholds, not pass or fail lines. Each workload is reported
on its own. Workloads are not pooled, and none is dropped after results exist.

## Setup

- **Host and virtual machine:** Apple M2 Pro under macOS 27.2. QEMU 11.1.3, `-accel hvf`, machine
  `virt`, 4 vCPUs, 2 GiB RAM, for both systems. The same QEMU binary and the same machine options are
  used for the seL4 guest and the Linux guest, and both run on the same host in alternating order
  (seL4, Linux, seL4, Linux) so that host drift hits both. Core-type observation, host power and
  thermal records follow the [C1 method](C1-method.md#hardware-and-setup).
- **Linux guest:** a pinned image, whose identity and SHA-512 are recorded in the
  [prerequisites](../../../docs/research/sel4-spike-prerequisites.md) before the first run. Kernel
  command line adds `transparent_hugepage=never`, so that huge pages do not remove faults. All other
  defaults stay as shipped, and the kernel version and `fault_around_bytes` are recorded.
- **seL4 side:** the B3 pager, on the Stage B kernel configuration. The results file states the
  configuration, its label (U, or M with a patch), and whether it is MCS.
- **Harness:** the same Rust crate, built for each target in release mode. The seL4 build and the
  Linux build (static `aarch64-unknown-linux-musl`) share the workload code and differ only in the
  memory-mapping layer.
- **Page size:** 4 KiB on both. Region sizes are fixed below.
- **Timing source:** the virtual counter, as in C1. A batch is 1,024 pages. The C1 resolution rule
  applies: one tick must be under 1% of the batch, so a batch must last at least 100 ticks (about
  4.2 µs at 24 MHz). A fault costs far more than 4 ns, so a real batch lasts far longer than that
  [Inferred]. The harness records the tick count of every batch, and the results file lists any
  batch under 100 ticks.

## Workloads

Each workload touches one byte per page, in the order stated, and times batches of 1,024 pages.

| ID | Workload | Region | Order | Setup before timing | Operation timed |
|---|---|---|---|---|---|
| F1 | First-touch anonymous | 128 MiB (32,768 pages), fresh mapping | Sequential | Mapping created, nothing touched | Write one byte to each page |
| F2 | File-backed read | 128 MiB file, fully resident in the page cache or the pager's store | Sequential | File written, every page confirmed resident (`mincore` on Linux, the pager's residency table on seL4) | Read one byte from each page |
| F3 | Copy-on-write | 128 MiB private mapping of the same file | Sequential | Every page first read, so each is mapped read-only | Write one byte to each page |
| F4 | Mixed | 64 MiB working set (16,384 pages) over three regions | Random, fixed seed (below), same sequence on both systems | As F1, F2 and F3 for their regions | 50% anonymous first-touch writes, 30% file-backed reads, 20% copy-on-write writes, in one pass |

Notes:

- F3 starts from the state F2 leaves. Each workload runs on its own fresh mapping, and F3 maps the
  file again, so F2 does not warm F3.
- The file is on the guest's regular root filesystem on Linux, not tmpfs, because tmpfs shares a
  different fault path from a page-cache file. On seL4 the file is an in-memory store owned by the
  pager. The results file states this difference. Disk reads never happen in a timed phase.
- F4 uses the 64-bit seed `0x0F1A2B3C4D5E6F70`. The sequence is generated by a fixed algorithm
  (`xorshift64*`) written in the harness, so both systems get the same order.

## Counting and reporting

- **Headline figure: cost per page touched**, which is total batch time divided by 1,024 pages. Both
  systems touch the same pages, so this is the same work. Linux may map several pages per fault
  because of fault-around, and a pager may do the same.
- **Also reported: cost per fault taken**, with the fault count from `getrusage` (`ru_minflt`) on
  Linux and from the pager's own counter on seL4. The two figures are reported side by side and
  never mixed.
- **Fault-around control:** for F2, Linux is run twice, once with the shipped `fault_around_bytes`
  and once with it set to 4096 in the guest, so that one fault maps one page. The 3-times comparison
  uses the shipped setting as headline and states the second as a sensitivity result.
- **Runs:** 30 per workload per system, each in a fresh VM boot, alternating as above.
- **Batches:** all 32 (F1 to F3) or 16 (F4) batches of every run are kept. The first batch of a run
  is not discarded, because first-touch cost is the measurement.
- **No outlier removal.** Every batch enters the statistics.
- **Per-run statistics:** median and 99th percentile of the batch results.
- **Reported across runs:** median of run medians (the headline), minimum and maximum run median,
  interquartile range, and the median of run 99th percentiles, for each system and workload.
- **Ratio:** seL4 headline divided by Linux headline, per workload, with the ratio's range computed
  from the minimum and maximum run medians of both. The 3 times threshold is tested on the headline
  ratio.

## Cause analysis above 3 times

The results file does not guess at causes. For any workload above 3 times it records:

- **Where the time goes:** a split of the seL4 fault path into kernel fault delivery, pager
  handling and mapping calls, by timing the stages in the pager with the same counter.
- **Design versus setup:** the cost of a kernel-entry loop (`seL4_Yield`) and of a bare Linux
  syscall loop (`getppid`) timed the same way, as a measure of per-exception cost under HVF.
- **Fix candidates:** batching map calls, mapping several pages per fault, or a faster pager path.
  Each candidate is a separate experiment with its own record. It does not change this method.

Above 5 times the same record adds a profile and the classification the plan requires.

## Records

Each C2 results file contains, in addition to the plan's list: this file's commit SHA, the Linux
image name and SHA-512, the Linux kernel version and command line, `fault_around_bytes`, the QEMU
command, `CNTFRQ_EL0` per run, the host power and thermal output, per-run fault counts, and the raw
batch data.

## Known limits

- HVF adds a cost to every guest exception on both systems. It cancels in the ratio only if it is
  the same on both, which is not shown. [Inferred]
- The Linux guest has a general-purpose memory manager and the seL4 side has one purpose-built
  pager. The ratio compares those two designs and says nothing about a mature seL4 pager.
- One region size per workload. The result is not a scaling curve.
- The memory is warm in the host's cache hierarchy after the first run in a series. Fresh VM boots
  reduce this and do not remove it.
