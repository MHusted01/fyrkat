## Command

```
spikes/sel4-feasibility/build.sh
```

It removes `build/`, then builds seL4, the kernel loader, `add-payload`, the Rust root task and the
boot image, and writes `build/SHA256SUMS`. It installs nothing. Natively on macOS arm64, no container.

**Documented cause of the `image.elf` difference** [Measured]:

1. QEMU writes random `rng-seed` and `kaslr-seed` properties into `/chosen` of the device tree it dumps.
   Two dumps with identical arguments differ in exactly those two properties and nothing else.
2. seL4's CMake dumps that tree from QEMU on every configure (`src/plat/qemu-arm-virt/config.cmake`
   passes `dumpdtb=`), and the tree is embedded verbatim in `image.elf` (found at byte offset 2,389,396).
3. `add-payload` is deterministic: three runs on fixed inputs gave identical bytes, equal to run 2's image.
4. The kernel, loader and root task are identical across the builds.

The difference is therefore random seed bytes in the embedded device tree, not the toolchain. A fully
identical image would need a fixed device tree. That is not done here.

## Findings

1. **The `cc` crate uses macOS's `ar` and `ranlib` on AArch64 ELF objects and loses the loader's assembly.**
   Without `AR_aarch64_unknown_none=aarch64-elf-ar` and `RANLIB_aarch64_unknown_none=aarch64-elf-ranlib`
   the loader builds without error but is 5.9 KB with entry point 0 and only a linker note, "cannot
   find entry symbol `_start`" [Measured: [first build](A1/12-loader-build.txt)]. With them it is 63 KB
   with a real entry point ([second build](A1/12b-loader-build-ar-fixed.txt)). The upstream recipe assumes
   Linux binutils. `build.sh` sets both.
2. **Python 3.15 cannot install `sel4-deps` from wheels.** `pyyaml` has no cp315 wheel [Measured]. `pyfdt`
   0.3 is source-only for every Python version, so the install needs `setuptools`, `wheel` and
   `packaging` (`wheel`'s own dependency). The owner approved the first two, hash-pinned, and Python
   3.12.16. `packaging` came with `wheel` and is on the record here.
3. **`cargo deny`** with the spike-local policy ([deny.toml](../deny.toml)):
   - spike workspace: advisories ok, bans ok, sources ok ([14](A1/14-deny-spike-workspace.txt));
   - rust-sel4 checkout, loader and `add-payload` only: **sources ok, advisories and bans failed**. The one
     advisory is `RUSTSEC-2024-0449`, `unsafe-libyaml` unmaintained, reached through `serde_yaml` in the
     host-side `add-payload` tool and a build script. The bans failures are all `wildcard` errors on
     rust-sel4's own first-party path dependencies ([11](A1/11-deny-sel4-kernel-loader.txt),
     [11](A1/11-deny-sel4-kernel-loader-add-payload.txt));
   - the whole rust-sel4 workspace also fails on `rsa`, `time` and `ttf-parser` advisories, in examples
     and tests that are not built ([10](A1/10-deny-rust-sel4.txt)).
   The policy was not weakened. Nothing here is an unapproved origin. The dependency path is traced in [19](A1/19-unsafe-libyaml-path.txt):
   `unsafe-libyaml` is reached only through `serde_yaml`, as a build-dependency of `sel4-platform-info` (a
   host-side build script) and as a dependency of the host-side `add-payload` tool. Both parse
   `platform_gen.yaml`, generated by the pinned seL4 build in our own install prefix. It is absent from
   the target loader's normal dependencies (`cargo tree -e normal` is empty), has no symbol or string in
   the built loader, and is not in the spike workspace's lock [Measured]. The advisory class is
   "unmaintained", not a vulnerability. No replacement was introduced and the policy is unchanged.
4. **Homebrew.** Installing `aarch64-elf-gcc` would have upgraded `lz4` 1.10.0 to 1.11.0 as a dependency,
   even with `lz4` pinned [Measured: [dry run](A1/02-brew-dryrun-lz4-pinned.txt)]. To keep decision 7's
   no-drift rule, both formulas were installed with `--ignore-dependencies`, which Homebrew calls an
   unsupported option. The compiler runs and links against the existing libraries. The Homebrew state
   differs from the baseline by exactly the two new formulas ([04](A1/04-brew-after.txt)).
5. **Nightly Rust is required, and these force it.** `-Z build-std` (the custom target
   `aarch64-sel4.json` needs `core` built from source), `-Z unstable-options`, and the crate features
   `linkage`, `never_type`, `proc_macro_hygiene`, `stmt_expr_attributes`, `cfg_target_thread_local`,
   `thread_local`, `core_intrinsics` and `panic_can_unwind` in the rust-sel4 crates the root task links.
   [Measured: grep of `#![feature]` in those 23 crates at `c819c27`]
6. The kernel linker warns that `kernel.elf` has a LOAD segment with RWX permissions. It is upstream's
   and is recorded.

## Deviations from the approved text, with their basis

- Python 3.12.16 instead of 3.15, and `setuptools`, `wheel`, `packaging`: owner answers of 2026-11-08.
- `bindgen` 0.72.1 as locked at `v6.0.0`, and member-crate manifests inside the spike workspace: owner

- `--ignore-dependencies` for the two Homebrew formulas, and `lz4` pinned: finding 4. This is the
  agent's choice to honour decision 7, and the owner may want to review it.
- Environment variables for the cross `ar` and `ranlib`: finding 1.

## Limitations

- Both builds ran on one machine, in one directory, minutes apart. This shows no cross-machine or
  cross-path reproducibility.
- The image has not been booted. Booting is A3.
- Crates and git dependencies were fetched from the network into the Cargo cache, which is shared and
  not part of the clean state. The lock files were enforced (`--locked`).
- The 30-minute and Linux-guest parts of the plan do not apply to A1.
