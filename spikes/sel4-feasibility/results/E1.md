## What the evidence shows

- **The kernel configuration differs from the A1 rerun's kernel in exactly one key** out of 156: `ARM_HYPERVISOR_SUPPORT`
  (False to True) [Measured: [05](E1/05-config-diff-vs-a1rerun.txt)]. The configuration is stored as [02](E1/02-kernel-gen_config.json)
  and [03](E1/03-kernel-cmake-cache.txt).
- **The A3 log 02 failure did not recur.** There the loader entered a non-hypervisor kernel at EL2 and took an instruction abort at
  `kernel_entry` `0xffffffffc0000000`. Here `kernel_entry` is `0xffc0000000` and the kernel boots [Measured: [A3 log 02](A3/02-boot-tcg-virt-1cpu.txt) against
  [boot 1](E1/10-boot-1.txt)]. That a matching kernel and loader were the missing piece is [Inferred]: it fits, and no other variable was
  isolated.
- **That one key has consequences the key count hides** [Documented: seL4 `src/plat/qemu-arm-virt/config.cmake` and its
  `overlay-reserve-vm-memory.dts`; Measured: [boot 1](E1/10-boot-1.txt), the CMake caches, `readelf`]. With hypervisor support on, seL4's CMake dumps the
  device tree with `virtualization=on` and adds an overlay that reserves `0x40000000` to `0x60000000` for a VM. In E1 the usable RAM
  is one region, `[60000000..80000000)`, which is **512 MiB**; the kernel's physical base is `0x60000000` (A1: `0x40000000`); and
  `KernelDTBSize` is 8115 (A1: 7916, from the local `build/` CMake cache, which is not published). This follows from the authorized option with no source change, so it is not stop condition (g).
  **Anyone using E1-H as a development baseline gets half the RAM**, which matters for the memory-sensitive Stage B and C work.
- **All four hashes are E1's own and differ from the A1 rerun's** [Measured]. The kernel differs because a build option changed. The loader
  and root task read the kernel's install directory [Inferred]. The root-task ELF also embeds its own target-directory path
  (`…/external/e1-build/root-task-target/…` here, `…/build/root-task-target/…` in A1) [Measured: `strings`], so its hash would differ
  from A1's even with an identical kernel. The hashed build-script directory name inside that path is the same in both builds, which
  fits an identical dependency set [Inferred]. The loader embeds no such path [Measured].

## Limitations and unresolved risks

- **One image, one build.** E1 did not repeat the build, so it makes **no reproducibility claim** for the E1 image. The three boots are of
  the same image (the reviewer's extra boot was too).
- **Half the RAM.** E1-H has one 512 MiB usable region at `0x60000000` because of the hypervisor option's device-tree overlay (see "What the
  evidence shows"). Results from E1-H are not comparable with A1/K1's memory layout.
- **The kernel prints `Warning: Could not infer GIC interrupt target ID, assuming 0.`** in all three boots. It is not a failure by the
  specification's definition. It comes from `infer_cpu_gic_id` in seL4's `gic_v2.c`, which prints it when the GIC's `ITARGETSR` reads zero;
  that fits a single-CPU GICv2 and is [Inferred], not tested. **This is the project's first GICv2 boot**: the passing A3 TCG control used
  `gic-version=3`, so the warning has no earlier baseline.
- **`TEST_PASS` is the end of the observation.** The harness stops at the marker. The root task then suspends itself, and E1 does not show
  the system staying up afterwards.
- **Three boots on one host, one vCPU, one CPU model, TCG only.** Nothing is claimed for another QEMU version, host or emulator
  setting. CI uses QEMU 8.2.2, not the 11.1.3 used here. E1's own preflight records `Darwin 27.2.0 arm64` and the seven Homebrew pins, not
  the CPU model or a Homebrew inventory hash as the A1 rerun's does: the host is the Apple M2 Pro of the earlier results [Measured: A1/00-baseline.txt],
  and the reviewer found no Homebrew or rustup change during E1 [Measured by the independent reviewer, from file modification times; not reproducible from the repository].
- **The kernel is unverified (label U).** Per the plan, no `qemu-arm-virt` run is ever a verified (V) configuration, and E1-H also has
  `KernelVerificationBuild=OFF` and debug and printing on [Documented: plan, Labels; Measured: `E1/03`]. The reference configuration
  K0 sets hypervisor support ON [Documented: seL4 `configs/include/AARCH64_verified_include.cmake`, line 13], so hypervisor support is not what makes E1-H unverified. E1 adds no assurance cell and changes no A2
  classification.
- **The linker prints a warning** that `kernel.elf` has a LOAD segment with RWX permissions. It is upstream's and was also recorded
  for A1.
- **Sanitized boot logs use LF line endings;** the raw logs have CRLF. The manifest records both hashes.
- **Commands.** The build was run as `bash -c 'set -o pipefail; ./build-e1.sh 2>&1 | tee results-raw/E1/01-build.txt; echo
  "BUILD_EXIT=${PIPESTATUS[0]}" | tee -a results-raw/E1/01-build.txt'`. Each boot was
  `python3 -I boot-image.py --virt --timeout 120 --marker TEST_PASS external/e1-build/image.elf`. `E1/00` and `E1/04` were written by shell
  `echo` and `git`/`shasum`/`brew` commands in the session, and **are not produced by a script in the repository**. `E1/03` is a 178-line
  excerpt (every line genuine) of the 983-line `CMakeCache.txt`: the lines starting `Kernel`, `ARM_CPU`, `CROSS_COMPILER`, `CMAKE_INSTALL_PREFIX`
  or `CMAKE_BUILD_TYPE`. `E1/05` was produced by a short inline Python comparison that is **described** in that file, not stored as a script.
- **Verifier scope.** The 15 E1 checks read only the sanitized files. They cannot show that the raw logs were not edited, which is true of
  the A1 and A3 checks as well. The kernel-configuration check now compares `E1/02` with the published `A1/kernel-gen_config.json`; the
  A1 rerun's build is compared only through the record in `E1/05`. Whether any build or boot attempt was made and discarded before the
  recorded ones cannot be shown from the disk, because `build-e1.sh` deletes its output first; the agent states it made none [not verifiable from the disk].
