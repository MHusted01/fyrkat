# A3 result: EL1 and HVF compatibility

- **Outcome: Fail**, by the plan's A3 Fail clause ("it cannot run under HVF"). Label **U**. **For the
  owner to confirm**, because the consequence is large (below).
- **Plan:** [seL4 feasibility spike plan](../../../docs/research/sel4-spike-plan.md), approved at
  `46a90fa`, with the owner's decisions of 2026-11-08 in its Amendments.
- **Date:** 2026-11-08. **Run by:** Sonnet.
- **Consequence per the plan's Consequences table:** "A3 Fail: reopens ADR 0002. Stage C does not run.
  Stop and report." Work stopped here. A4 and A2a were not started.

## What was run

An AArch64 `qemu-arm-virt` build of unmodified seL4 17.0.0 (`62e345c`), **without** hypervisor support,
as the sel4test suite, loaded by seL4's own elfloader, under QEMU 11.1.3 with `-accel hvf -cpu host`,
GICv3, 1 and 4 vCPUs, on the Apple M2 Pro host. No kernel change.

| Configuration | Result |
|---|---|
| HVF, 1 vCPU | **Does not boot.** `ERROR: kernel requires 16-bit ASIDs`, then the kernel halts ([10](A3/10-boot-sel4test-hvf-1cpu.txt)) |
| HVF, 4 vCPUs | **Does not boot.** Identical failure ([13](A3/13-boot-sel4test-hvf-4cpu.txt)) |
| TCG control, 1 vCPU, Cortex-A57 | **Boots**: "Booting all finished, dropped to user space", "Starting test suite sel4test", tests running ([14](A3/14-boot-sel4test-tcg-1cpu-control.txt)). The suite was not run to completion in the 60 s allowed |

The control uses the same image. The failure is specific to HVF and is not a build fault.

## Root cause [Measured]

Non-hypervisor AArch64 seL4 refuses to start unless `ID_AA64MMFR0_EL1.ASIDBits` reports 16-bit ASIDs and
`TCR_EL1.AS` is set (`check16BitASID()` in `include/arch/arm/arch/64/mode/machine.h`, called from
`src/arch/arm/kernel/boot.c`). A probe that prints the ID registers from inside each guest
([probes/idregs.c](../probes/idregs.c), [11](A3/11-probe-idregs.txt)) shows:

| Guest | `CurrentEL` | `MIDR_EL1` | `ID_AA64MMFR0_EL1` | ASIDBits |
|---|---|---|---|---|
| TCG, Cortex-A57 | EL1 | `411fd070` | `…1124` | **2 (16-bit)** |
| HVF, `-cpu host` (M2 Pro) | EL1 | `610f0000` | `…000010000f100002` | **0 (8-bit)** |

So the guest that Hypervisor.framework presents has 8-bit ASIDs. Whether that is the chip or a mask
applied by the framework is not established. It was measured on one host only.

## Why no kernel change is available

- Removing the check, or changing the kernel to manage 8-bit hardware ASIDs, touches address-space
  isolation and TLB maintenance and weakens a check. The plan's Kernel modification policy puts that in
  **Class 3**: "unacceptable in this spike at any size, and never attempted in it. An experiment that
  needs one is a Fail." It is not a Class 1 platform or timer fix, so the A3 Conditional clause does not
  apply. Nothing was patched.
- The hypervisor-mode kernel avoids this check but needs EL2. This host cannot give an HVF guest EL2:
  `qemu-system-aarch64: -accel hvf: Nested virtualization not supported on this system` ([04](A3/04-boot-hvf-virt-1cpu.txt)).

## Other findings

1. **`sel4-kernel-loader` v6.0.0 supports only EL2 on AArch64.** It asserts `CurrentEL == EL2`, switches
   EL2 translation tables and jumps to the kernel at EL2, never dropping to EL1
   (`crates/sel4-kernel-loader/src/arch/arm/arch/aarch64/mod.rs`) [Documented: source]. The A1 image (hypervisor off) crashed in it. Started at EL1 it printed nothing
   ([01](A3/01-boot-tcg-1cpu.txt)); a QEMU `-d guest_errors,int` trace showed an undefined-instruction
   fault on a read of `SCTLR_EL2` [Measured; the 32-million-line trace was not kept]. Started at EL2 under
   TCG the loader runs and prints, then the kernel faults at its entry
   ([02](A3/02-boot-tcg-virt-1cpu.txt)). The A1 image therefore has not been booted
   successfully. This matters for A4, which compares loaders.
2. **HVF cannot emulate GICv2** (`HVF does not support GICv2 emulation`, [03](A3/03-boot-hvf-el1-1cpu.txt)),
   which is seL4's default for `qemu-arm-virt`. A3 uses GICv3 (`-DQEMU_GIC_VERSION=3`).
3. **sel4test on macOS needed three workarounds**, none touching the kernel:
   - Homebrew `protoc` 36.2 cannot pair with the venv's Python `protobuf` 3.20.3 (`sel4-deps` pins
     `<4`). No Python file in the kernel, `seL4_tools` or the projects imports `protobuf`; only nanopb's
     generator does, and sel4-deps's own comment says the pin exists for Ubuntu 22.04's protoc [Measured].
     Rather than override the pin, `build-protoc.sh` builds **protoc 3.20.3 from the pinned source commit
     `fe271ab7…`** into the gitignored `external/` (16 s; no Rosetta, nothing installed). The
     `protobuf` 7.36.2 override the owner conditionally approved was **not needed or used**.
   - macOS `cpio` lacks the GNU options `--append`, `--reproducible` and `--owner` that seL4's
     `cmake-tool` uses. [`tools/cpio`](../tools/cpio) is a small stdlib-only stand-in for exactly
     that subset, validated by reading its archives back with macOS `cpio`. **It is custom spike code
     and was not individually approved.** The owner may want to review it.
   - musllibc's build runs `rm src/.git`, expecting a `repo`-style `.git` file. `fetch-sel4test.sh` uses
     `git init --separate-git-dir` so `.git` is a file. It uses plain git, not `repo`.
4. `opensbi` from the sel4test manifest was not fetched (RISC-V only). All other nine pins verified
   ([06](A3/06-fetch-sel4test.txt)).

## Limitations

- One host (Apple M2 Pro). Other Apple chips may present 16-bit ASIDs through HVF. This was not tested.
- sel4test was not run to completion on any configuration. Under HVF it never got past kernel init.
- The TCG control used one vCPU only.
- HVF is U at best and says nothing about hardware.

## What the owner needs to decide

- Whether to accept the plan's reading, A3 Fail, which reopens ADR 0002 (native execution on the Mac)
  and stops Stage C.
- The plan names no path that keeps HVF and unmodified seL4 on this host. Options the plan does not
  authorize, for the owner to weigh: a Class 3 kernel change (excluded by the plan), a different host chip,
  or running seL4 under TCG with the loss of native speed (which would make Stage C numbers meaningless
  for the native-execution argument).
