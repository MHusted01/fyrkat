## Correction to the first report of this result

The first version of this record, and the report given to the owner, said unmodified seL4 failed the
ASID check under HVF "with 1 and 4 vCPUs", and that the sel4test suite had only started under TCG. An
independent review of the evidence showed three errors, now fixed:

1. **The "4 vCPU" image was a single-node kernel.** sel4test ignores `NUM_NODES` unless `SMP=TRUE`, so the
   first image had `KernelMaxNumNodes=1` and was only run with QEMU `-smp 4`. The first-run logs are kept in
   [shim-era/](A3/shim-era/) as history. The repeat below builds a real 4-node SMP kernel, and its recorded
   configuration is published: [41](A3/41-config-1cpu.txt) and [42](A3/42-config-4cpu.txt).
2. **sel4test completed under TCG.** The control run finished: "Test suite passed. 124 tests passed. 59
   tests disabled." in 21 s. The record said it was not run to completion.
3. **GNU cpio was already installed.** The first sel4test builds used a custom stand-in. The repeat uses the
   installed GNU cpio 2.15 instead (see [deviations](deviations.md), D1).

## What was run (repeat, with GNU cpio and a real SMP kernel)

Unmodified seL4 17.0.0 (`62e345c`) as the sel4test suite, `qemu-arm-virt`, AArch64, **without**
hypervisor support, GICv3, seL4's elfloader, QEMU 11.1.3, Apple M2 Pro host, no kernel change.

| Configuration | Result |
|---|---|
| HVF, 1 vCPU | **Does not boot.** `ERROR: kernel requires 16-bit ASIDs`, kernel halts ([31](A3/31-boot-hvf-1cpu.txt)) |
| HVF, 4 vCPUs, 4-node SMP kernel | **Does not boot, for a different first reason.** The elfloader aborts before the kernel starts: `HVC is not supported for PSCI! Failed to boot cpu 0x1` ([32](A3/32-boot-hvf-4cpu-smp.txt)). The kernel's ASID check was **not reached**, so it was not measured on the SMP kernel |
| TCG, 1 vCPU, Cortex-A57 (control) | **Boots and passes**: 124 tests passed, 59 disabled, 21 s ([33](A3/33-boot-tcg-1cpu-control.txt)) |
| TCG, 4 vCPUs, 4-node SMP kernel (control) | **Same PSCI abort as HVF** ([34](A3/34-boot-tcg-4cpu-smp-control.txt)). The 4-node image has not been shown to boot anywhere |

The configuration of both images is published as evidence, not only described: [41](A3/41-config-1cpu.txt)
(`MAX_NUM_NODES` 1, SMP off, hypervisor support off, `qemu-arm-virt`, Cortex-A53 kernel, one cpu node) and
[42](A3/42-config-4cpu.txt) (`MAX_NUM_NODES` 4, SMP on, same otherwise, four cpu nodes). `verify-evidence.py`
checks those values, not only that the files exist.

The 4-vCPU PSCI abort happens in seL4's unmodified elfloader and under TCG as well as HVF. The device tree, dumped at configure time with
`virt,secure=off`, says PSCI `method = "hvc"`, and the elfloader supports only the SMC conduit when
bringing up secondary CPUs (`elfloader-tool/src/arch-arm/drivers/smp-psci.c`) [Documented: source;
Measured: the log and the published DTB excerpt, [41](A3/41-config-1cpu.txt) and
[42](A3/42-config-4cpu.txt)]. The abort comes from the elfloader rejecting the HVC conduit
(`smp-psci.c`, "HVC is not supported for PSCI"). It is a loader limitation, not a kernel one, and a change
to the loader or to the machine's PSCI conduit might get past it. The result is therefore **not** evidence
that SMP cannot work on this host. Under HVF this host has neither EL3 (`secure=on`) nor nested EL2 to
change the conduit [Inferred]. Whether some other machine or device-tree setting makes the 4-node kernel boot
under TCG was **not investigated**, to keep within the stop condition.

## Why the Fail stands

The A3 Fail clause is "it cannot run under HVF". The 1-vCPU run shows that with no kernel patch, and the
plan's Pass needs "boots and passes on both vCPU counts". The 4-vCPU run adds no evidence in HVF's favour: it
stops in the elfloader before the kernel, and under HVF this host has no way to change the conduit
[Inferred]. No workaround was investigated. The plan's Investigate clause ("only 1 vCPU works") does not
fit, because 1 vCPU does not work either.

## Decision rule 2: the owner's ruling of 2026-11-08

The plan has two statements that fit this result, and an earlier version of this record applied only the
first. The Consequences row says "A3 Fail: reopens ADR 0002. Stage C does not run. Stop and report", and the
A3 clause says a Fail "does not falsify the hypothesis alone". Decision rule 2 says the hypothesis is
falsified "if an experiment needs a Class 3 kernel change". The agent did not settle that conflict. **The owner
ruled that decision rule 2 applies**, because the tested HVF-specific configuration fails the approved A3
requirement and passing it would need a prohibited Class 3 kernel change under the options now available
(next section). That ruling is recorded in the plan's Amendments.

What the ruling covers, and what it does not:

- It covers **this HVF-specific configuration**: unmodified non-hypervisor seL4 17.0.0 booted under QEMU's
  HVF accelerator on one Apple M2 Pro.
- It is **not** a rejection of seL4 on TCG, on other hardware, or on another Apple chip. Under TCG the same
  kernel passes sel4test (124 passed, 59 disabled).
- seL4-first and AArch64-first stay only as **provisional, broader hypotheses**, subject to the reopened
  architecture decision. ADR 0002 stays Provisional and ADR 0004 stays Proposed. No ADR was edited.

## Root cause of the 1-vCPU failure [Measured]

Non-hypervisor AArch64 seL4 refuses to start unless `ID_AA64MMFR0_EL1.ASIDBits` reports 16-bit ASIDs and
`TCR_EL1.AS` is set (`check16BitASID()` in `include/arch/arm/arch/64/mode/machine.h:152`, called from
`src/arch/arm/kernel/boot.c:196`) [Documented: source]. A probe that prints the ID registers from inside
each guest ([probes/idregs.c](../probes/idregs.c), [11](A3/11-probe-idregs.txt)) shows:

| Guest | `CurrentEL` | `MIDR_EL1` | `ID_AA64MMFR0_EL1` | ASIDBits |
|---|---|---|---|---|
| TCG, Cortex-A57 | EL1 | `411fd070` | `…1124` | **2 (16-bit)** |
| HVF, `-cpu host` (M2 Pro) | EL1 | `610f0000` | `…000010000f100002` | **0 (8-bit)** |

The guest that QEMU's HVF accelerator presents has 8-bit ASIDs. Whether the value comes from the chip, from
a mask applied by Hypervisor.framework, or from QEMU is **not established**. One host was measured.

## Why no kernel change is available

- Removing the check, or changing the kernel to manage 8-bit hardware ASIDs, touches address-space
  isolation and TLB maintenance and weakens a check. The plan's Kernel modification policy puts that in
  **Class 3**: "unacceptable in this spike at any size, and never attempted in it. An experiment that
  needs one is a Fail." It is not a Class 1 platform or timer fix, so the A3 Conditional clause does not
  apply. Nothing was patched.
- The hypervisor-mode kernel avoids the ASID check but needs EL2. This host cannot give an HVF guest EL2:
  `qemu-system-aarch64: -accel hvf: Nested virtualization not supported on this system`
  ([04](A3/04-boot-hvf-virt-1cpu.txt)).

## Other findings

1. **`sel4-kernel-loader` v6.0.0 supports only EL2 on AArch64.** It asserts `CurrentEL == EL2`, switches EL2
   translation tables and jumps to the kernel at EL2, never dropping to EL1
   (`crates/sel4-kernel-loader/src/arch/arm/arch/aarch64/mod.rs:60`) [Documented: source]. The A1 image
   (hypervisor off) crashed in it. Started at EL1 it printed nothing ([01](A3/01-boot-tcg-1cpu.txt)); a QEMU
   `-d guest_errors,int` trace showed an undefined-instruction fault on a read of `SCTLR_EL2` [Inferred: observed in the session, not retained; the 32-million-line trace was not kept]. Started at EL2 under TCG the loader runs and prints,
   then the kernel faults at its entry ([02](A3/02-boot-tcg-virt-1cpu.txt)). The A1 image has therefore not
   been booted successfully. This matters for A4, which compares loaders.
2. **HVF cannot emulate GICv2** (`HVF does not support GICv2 emulation`, [03](A3/03-boot-hvf-el1-1cpu.txt)),
   which is seL4's default for `qemu-arm-virt`. A3 uses GICv3 (`-DQEMU_GIC_VERSION=3`).
3. **sel4test on macOS needed these workarounds**, none touching the kernel:
   - Homebrew `protoc` 36.2 cannot pair with the venv's Python `protobuf` 3.20.3 (`sel4-deps` pins `<4`).
     [Inferred: observed in the session; the failing log was overwritten.] No Python file in the kernel,
     `seL4_tools` or the projects imports `protobuf`; only nanopb's generator does [Measured: grep].
     sel4-deps's own comment says the pin exists for Ubuntu 22.04's protoc [Documented:
     `external/seL4/tools/python-deps/setup.py:48-51`]. `build-protoc.sh` builds
     **protoc 3.20.3 from the pinned source commit `fe271ab7…`** into the gitignored `external/` (16 s,
     [09](A3/09-protoc-3.20.3-build.txt)). The `protobuf` 7.36.2 override the owner conditionally approved was
     **not used**.
   - seL4's `cmake-tool` needs GNU cpio options that macOS `cpio` lacks. GNU cpio 2.15, already installed
     as the keg-only Homebrew formula `cpio`, is put on `PATH` for the build only.
   - musllibc's build runs `rm src/.git`, expecting a `repo`-style `.git` file. `fetch-sel4test.sh` uses
     `git init --separate-git-dir`. It uses plain git, not `repo`.
4. The sel4test kernels are built for a Cortex-A53 (`KernelArmCPU=cortex-a53` in both CMake caches), unlike
   the A1 kernel (Cortex-A57). The TCG controls ran with `-cpu cortex-a57`. This was not varied. The HVF runs
   use `-cpu host`, so the kernel's target CPU does not decide the ASID result, which comes from the guest
   ID registers [Inferred].
5. `opensbi` from the sel4test manifest was not fetched (RISC-V only). The eight project pins were verified
   ([06](A3/06-fetch-sel4test.txt)) and the kernel pin was verified for A1 ([A1/07](A1/07-fetch-sources.txt)).

## Limitations

- One host (Apple M2 Pro). Other Apple chips may present 16-bit ASIDs through HVF. This was not tested.
- sel4test never got past kernel init under HVF, so no test ran under HVF.
- The 4-node SMP kernel was never booted successfully. Its ASID behaviour under HVF is unmeasured.
- The sel4test "clean" builds reuse a cached musllibc from `external/sel4test-workspace/.sel4_cache`
  ("Found valid cache entry" in [21](A3/21-build-1cpu.txt)).
- HVF is U at best and says nothing about hardware. The same holds for TCG: a TCG pass is useful for early
  development and testing, but it is **not** equivalent to hardware acceleration or to validation on
  physical hardware, and nothing here should be quoted as if it were.
